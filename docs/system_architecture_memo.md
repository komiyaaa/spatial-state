# システムアーキテクチャ 設計メモ(2026-08-06時点)

`spatial_id_design_memo.md`(データモデル・更新アルゴリズムの設計)を前提に、
それを実際に動かすシステム全体の構成を整理する。

---

## 1. コンポーネント一覧とデータフロー

```
[現地(スマホ)]
   生点群を計測(Scaniverse等、対象外)
        ↓
[Web UI - 追加モード]
   ラフレジストレーション(このUI上での手動位置合わせ)
        ↓
[別サーバー(位置合わせ、対象外)]
   ラフレジ済みデータ保存 → VGICP精密位置合わせ → JSON化(Local Spatial ID格子基準)
        ↓
[更新エンジン(非同期ジョブ)]
   Step1: ヒットした空間ID集合を求める
   Step2: 近傍のヒット密度から「今回のスキャンのカバー範囲」を推定
   Step3: 「カバーされたが非ヒット」の集合を求める(消失の証拠の対象)
   Step4: Step1・Step3の空間IDの行だけを更新する
   Step5: それ以外の空間IDは一切触らない
        ↓
[永続DB]
   BUILDING / LOCAL_SPACE / COORDINATE_DEFINITION
   SPATIAL_VOXEL / VOXEL_STATE / VOXEL_MOBILITY / VOXEL_LABEL
   OBSERVATION(監査ログ)
   STRUCTURAL_LABEL_POLICY / LABEL_MASTER
        ↓
[Web UI - ビューワモード]
   建物一覧 → ローカル空間一覧 → 3Dボクセルビューワ
```

`[ベースマップストア]`は建物ごとの単独データとして存在し、`COORDINATE_DEFINITION`
(結節情報)を介してビューワ上で接続表示される(DBとは別系統のアセットストア)。

### コンポーネントの役割

| コンポーネント | 責務 | 読み書き |
|---|---|---|
| Web UI(追加モード) | ラフレジストレーションの操作画面 | 別サーバーへ書き込み |
| 別サーバー(位置合わせ) | VGICP精密位置合わせ、JSON化。今回の設計スコープ外の既存の仕組み | - |
| 更新エンジン | Step1〜5の実行 | **DBへの読み書き両方**(下記参照) |
| 永続DB | ER図で定義した全テーブル | 更新エンジンが書き、Web UIが読む |
| Web UI(ビューワモード) | 建物/ローカル空間一覧、3Dボクセル表示 | DB・ベースマップストアを読む |

### 【重要】更新エンジンは書き込みだけでなく読み込みも行う

Step2(カバー範囲推定)の`agr`計算には近傍の情報が要るため、**新しく届いた
JSONの中だけでは完結せず、DBに既に保存されている近傍の空間ID(過去の観測)も
読みに行く必要がある。** 更新エンジンは書き込み専用ではなく、DBに対して
双方向にアクセスするコンポーネントとして設計すること。

### 未決定事項: 同期 or 非同期

現状は非同期ジョブ(キューに積んでバックグラウンド処理)を想定している。
理由は、1回のスキャンで数千〜数万の空間IDが更新対象になりうるため、
UIのリクエストを待たせたくないため。ただし「取り込んだらすぐ結果を見たい」
という運用要求があるなら、同期処理、または非同期のままUI側に処理中状態を
表示する仕組みが別途必要になる。

## 2. ディレクトリ構成(開発段階の想定)

```
project-root/
├── apps/
│   ├── web-ui/              # Web UI(ブラウザ側、今回のプロトタイプの発展形)
│   ├── api-server/          # Web UIが呼び出すAPI(建物一覧・ビューワ用データ取得)
│   └── update-engine/       # 非同期ジョブ(Step1〜5)
│
├── packages/
│   ├── core-model/          # pillar3_eval/core/ の発展形
│   │   ├── log_odds.py      # 既存
│   │   ├── confidence.py    # 既存
│   │   ├── state_machine.py # 既存
│   │   └── spatial_id.py    # 新規: 空間IDのエンコード/デコード、近傍計算
│   │
│   └── db-schema/           # ER図をマイグレーションとして定義したもの
│
├── infra/
│   └── docker-compose.yml   # DB・API・ジョブワーカーをまとめて起動する設定
│
├── data/
│   └── base_maps/           # ベースマップの実体(当面はローカルファイルでよい)
│
└── docs/
    ├── spatial_id_design_memo.md
    └── system_architecture_memo.md(本ファイル)
```

`packages/core-model/`は、これまで`pillar3_eval`で作ってきたコード
(`core/log_odds.py`, `core/confidence.py`, `core/state_machine.py`)の
延長線上にある。ゼロから作り直すのではなく、今のコードが本体に育っていく
想定。

---

## 3. 開発段階の実行環境: docker-composeで1台のPCに集約

本番用のクラウドサーバーは研究段階では不要。`docker-compose`で、DB用の
コンテナ(PostgreSQL等)とAPI/更新エンジン用のコンテナを同時に立ち上げ、
1台のPCの中で「別々のサーバーがある」状態を再現する。`docker-compose up`
一発でシステム全体が動く状態を目標とする。

## 4. 将来、実運用へ移行する際の変化

| 要素 | 研究段階 | 実運用 |
|---|---|---|
| DB | PC内のDockerコンテナ | クラウドの管理型DB |
| ベースマップ | ローカルファイル | クラウドのオブジェクトストレージ |
| 更新エンジン | 同じPC内のプロセス | クラウドのジョブキュー |
| 位置合わせサーバー | 既存のまま(スコープ外) | 既存のまま(スコープ外) |

ディレクトリ構成自体は大きく変えず、`docker-compose.yml`の中身を実際の
クラウドサービスを指す設定に差し替えるだけで移行できることを意識して
設計する(研究段階の作り込みを無駄にしないため)。
